# CountyIQ Intelligence Platform Repositioning

**Date:** 2026-04-03
**Status:** Draft
**Scope:** Product repositioning from data aggregator to intelligence platform

## Problem Statement

CountyIQ currently aggregates 21 public data sources for York County, PA and presents them through scored tables and data browsers. 11 of 17 API endpoints are raw data passthrough. The "intelligence" is 13 hand-picked signals with hand-picked weights summed into numeric scores (0-100 for momentum, 0-1 for distress). These scores are meaningless to users — a developer looking at "67" has no idea what to do with it, can't verify the claims behind it, and isn't given any actionable narrative about why the parcel matters.

The product needs to shift from "data browser with scoring veneer" to "intelligence platform that generates evidence-backed briefs with full provenance."

## Target Audience

Primary: Real estate developers and investors who need county-level intelligence to identify opportunities, assess risk, and make acquisition decisions.

Long-term: Any professional who needs county-level intelligence — attorneys, appraisers, municipal planners, economic development officers — served through persona-specific lenses on the same intelligence infrastructure (Phase C, future scope).

## Core Repositioning

### Before
- Numeric scores as user-facing output (67, 0.73)
- 13 signals with arbitrary weights summed into a number
- No evidence linking — users can't verify claims
- No narrative — users see data points, not intelligence
- Score-sorted tables (Development Radar, Distressed Parcels, Assemblage)

### After
- Intelligence briefs as the atomic unit of the product
- LLM reasoning agent validates signals and synthesizes narratives
- Every factual claim links to both the CountyIQ record and the original government source
- Scores become internal ranking only — users never see them
- Unified Intelligence Feed replaces score-sorted pages

## Three Output Layers

### 1. Parcel Briefs
Per-property intelligence narratives generated by the LLM reasoning pipeline. 2-4 paragraphs explaining what's happening, why it matters, and what the risks are. Every factual claim has citations linking to both internal records and original sources.

Each brief includes:
- Narrative text with inline evidence citations
- Qualitative assessment: `strong_opportunity | emerging | speculative | constrained | not_actionable`
- Assessment reasoning
- Key questions the reader should verify before acting (things the platform doesn't know)

### 2. County Narratives
Cross-parcel pattern detection identifying corridor trends, owner portfolio strategies, municipal development posture, and distress migration. Generated weekly from aggregated parcel briefs and signal data. Four narrative types:
- **Corridor activity** — clusters of development signals along road corridors
- **Owner portfolio** — entity strategies (assembly, distress, expansion)
- **Municipal trends** — ZHB decision patterns, development posture, distress concentration
- **Distress migration** — where tax distress is concentrating, spreading, or resolving over time

### 3. Evidence Layer
The structured citation backbone underneath both layers. Every signal carries: the claim, the specific data point, the internal record URL, the original source URL, validation status, and validation reasoning. Briefs are built from evidence; evidence is always accessible independently.

## New Data Sources

Two new data source pipelines are required to support the intelligence platform, particularly for entity resolution.

### PA DOS Corporate Entities
- **Source:** PA Department of State Corporation Bureau (corporations.pa.gov)
- **Access method:** Targeted lookups by entity names found in parcel ownership records
- **Flow:** Extract unique LLC/Corp/LP names from `staging.parcels` owner_full -> query PA DOS for each -> parse registration details
- **Target table:** `staging.corporate_entities`
- **Key fields:** `entity_name`, `entity_number`, `entity_type` (LLC/LP/Corp), `status`, `formation_date`, `registered_agent_name`, `registered_agent_address`, `office_address`, `officers` (JSONB array of name + title), `source_url`
- **Asset location:** `pipelines/countyiq/assets/scrapers/pa_dos_entities.py`
- **Frequency:** Weekly, after parcel refresh (needs current owner names)
- **County config:** Base URL added to `CountyConfig`
- **Intelligence unlock:** The single highest-value addition for entity resolution. Reveals the person behind the LLC, connects related entities through shared registered agents/office addresses.

### Public Proceedings (All 72 Municipalities)
- **Source:** All York County municipality websites + YCPC + county zoning hearing board
- **Access method:** Two-stage: (1) scraper discovers and downloads meeting minute documents (PDFs, HTML), (2) multimodal model (Gemma 4) reads page images and extracts structured records directly — no text extraction step, no format-specific parsers
- **Why multimodal:** 72 municipalities = 72 different document formats. Vision model handles all without per-municipality parsing logic.
- **County config:** `municipality_websites` dictionary mapping municipality names to meeting minutes URLs
- **Target tables:** `staging.public_proceedings` (document metadata) + `staging.proceeding_extractions` (structured records extracted by LLM)

#### staging.public_proceedings
- `id`, `body_name` (municipality/board), `meeting_date`, `proceeding_type` (planning_commission/zoning_hearing/council/supervisors), `raw_text`, `source_url`, `document_url` (link to original PDF)
- SCD Type 2 as standard

#### staging.proceeding_extractions
- `proceeding_id` (FK), `extraction_type` (rezoning_application/variance_request/conditional_use/subdivision_review/development_proposal), `applicant_name`, `parcel_reference` (PIDN or address), `current_zoning`, `proposed_zoning`, `decision` (approved/denied/tabled/continued), `conditions` (JSONB), `supporting_text` (exact quote from document), `extraction_confidence`, `model_used`, `page_number`

#### Asset locations
- Scraper: `pipelines/countyiq/assets/scrapers/public_proceedings.py`
- Extraction: `pipelines/countyiq/assets/enrichment/proceeding_extraction.py`

#### Scale
- 72 municipalities x ~12 meetings/year = ~864 documents/year
- ~5-10 pages each = ~6,000 page images/year
- ~1 second per page on 4090 with Gemma 4 = under 2 hours for full year backfill
- Weekly incremental: ~15-20 new documents = minutes of processing

### Source URL Provenance (Existing Tables)
All existing staging tables gain a `source_url TEXT` column, backfilled from county_config URLs where possible. This enables the evidence layer to link every claim to the original government source.

### Not In Scope
- **Recorder of Deeds** — being built separately, will integrate when ready
- **Court dockets** — per-parcel Playwright scraping is too slow and fragile. Revisit when the intelligence platform is running; at that point the LLM can identify which parcels warrant targeted lookup.
- **Building permits** — access uncertain, skip for now
- **Assessment data** — Tyler API access is being pursued separately

## LLM Architecture

### Reasoning Agent, Not Copywriter
The LLM is not a prose polisher. It is a reasoning agent that interrogates signal data, validates claims, cross-references across sources, and produces verified intelligence. The signals are input evidence, not a formula. The model reasons about whether the evidence supports a conclusion and shows its work.

### Dev/Prod Split
- **Development:** Local 4090 GPU, larger model (70B-class quantized), fast iteration on harness prompts and reasoning quality
- **Production:** Hetzner VPS (8GB dedicated, CPU-only), GGUF Q4_K_M via llama.cpp. CPU inference at ~10-20 tok/sec is sufficient for weekly batch processing. Dagster schedules the pipeline.
- **Model runtime:** llama.cpp for both dev (4090 CUDA) and prod (Hetzner CPU). Same GGUF format, same harness, different hardware.
- **Model selection:** Empirical, not prescribed. During Phase 2, build harness first, then create a test dataset of ~100 parcels with known signals. Run candidate models through the same harness, compare output quality on structured reasoning accuracy, citation correctness, and narrative coherence. Evaluate multimodal models (Gemma 4, etc.) for Pass 0 and text reasoning models for Passes 1-4 independently — may end up with one model or two depending on results. Current candidates include Qwen 3.5, Gemma 4, Llama 4, Phi-4, Mistral (latest) — test whatever is current at build time.

### Five-Pass Pipeline

```
weekly_data_refresh (existing)
  -> signal_extraction (existing, renamed from development_signals)

public_proceedings_scrape (new, weekly, all 72 municipalities)
  -> Pass 0: proceeding_extraction (multimodal LLM)

parcels_refresh (existing)
  -> pa_dos_entity_lookup (new)

All data assets complete
  -> Pass 1: entity_verification (per entity cluster)
    -> Pass 2: signal_validation (per signal per parcel)
      -> Pass 3: brief_generation (per parcel)
        -> Pass 4: county_narratives (per geography/theme)
```

Each pass is a Dagster asset. Incremental processing via `meta.intelligence_passes` — only re-run parcels whose input data changed (tracked by input hash).

## Pass 0: Document Intelligence

**Purpose:** Ingest unstructured sources (meeting minutes PDFs) into structured records.

**Model:** Multimodal (Gemma 4 or equivalent) — reads PDF page images directly.

**Harness:** Per-page prompt identifying municipality and meeting type, asking the model to extract rezoning applications, variance requests, conditional use permits, subdivision reviews, development proposals, and entity names. Output is structured JSON with supporting text quotes and confidence levels.

**Runs:** On ingest when new documents appear, not on the weekly analysis cycle.

## Pass 1: Entity Verification

**Purpose:** Cross-reference owner identities across all sources, resolve entities, build relationship graph.

**Unit:** Per entity cluster (candidates identified by SQL pre-filter).

### Stage A: SQL Pre-Filter (No LLM)
Identifies candidate entity clusters that need LLM reasoning:
- Same PIDN across sources (parcels + tax claims + subdivision filings)
- Name similarity > 0.5 via pg_trgm within the same municipality
- Same address appearing across sources with different owner names
- Sale chain connections (previous_owner matches current owner elsewhere)
- Shared substring patterns in LLC/business names
- PA DOS shared registered agent or office address

### Stage B: LLM Reasoning (Per Cluster)
The harness receives all records for a candidate cluster:
- Owner names from parcels + sale history + previous owners
- Tax claim owner names
- PLCB licensee + premises_owner names
- PA business registration names
- PA DOS: registered agent, officers, office address for every LLC/Corp
- Recorder of Deeds: grantor/grantee pairs, deed types (when available)
- Public proceedings: applicant names from meeting minutes/zoning hearings
- Address co-location across all sources

The LLM's job: determine which records belong to the same real-world entity, explain reasoning, identify relationship structures (person owns LLC, LLC holds properties), and flag rejected matches.

### Output
- `public.entity_graph` — verified entity relationships with confidence, reasoning, linked sources, relationships

### Scale
- ~176K parcels, most are straightforward single-owner matches
- SQL pre-filter reduces to ~10-20K clusters needing LLM reasoning
- ~500 tokens input + ~300 tokens output per cluster
- Clusters are independent, fully parallelizable

## Pass 2: Signal Validation

**Purpose:** Interrogate each signal on each parcel to determine if it's actually meaningful.

**Unit:** Per signal per parcel.

### Harness Structure
Each signal type has a static template with:
- **Base questions** (always asked) — signal-type-specific validation criteria
- **Conditional questions** (included only if relevant data exists) — cross-references to proceedings, deeds, corporate records, portfolio context

### Context Gathering (SQL, No LLM)
For each parcel/signal, Python queries gather:
- Parcel fundamentals (acreage, class, value, municipality, zoning)
- Entity graph from Pass 1 (who controls this parcel, related entities)
- Cross-parcel portfolio (other holdings by the same entity)
- Tax claims on this PIDN
- Proceedings mentioning this parcel or its owner entities
- Adjacent parcels with their signals and distress status
- Deed history (when available)
- PA DOS corporate records (if owner is an entity)

### Signal-Specific Validation

**active_subdivision:** Is the plan recent enough? Is the scale significant? Is the distance relevant? Does plan type match parcel potential? Any proceedings updates (approvals/denials/conditions)?

**tax_distress:** Chronic vs one-time? Amount relative to assessed value? Portfolio-wide pattern? Approaching judicial sale threshold? Any deed transfers suggesting exit? LLC still active per PA DOS?

**ownership_change:** Market transaction or non-arm's-length transfer? Distressed acquisition price? Buyer connected to other development activity via entity graph? Any post-acquisition proceedings or permit filings?

**zoning_mismatch:** Meaningful mismatch or labeling artifact? Future land use plan recency? Any active rezoning applications? Adjacent parcels also mismatched (corridor-level signal)? ZHB approval pattern in this area?

**vacancy:** Genuinely vacant or structures data gap? Assessed value consistent with vacant land? Duration of vacancy? Any demolition/environmental records in proceedings?

**assemblage:** Entity resolution changes ownership count? Delinquent neighbors in deep vs light distress? Geometry actually assemblable (contiguous block)? Total acreage meaningful for development? Any entity already assembling (deed records)?

**ecodev_candidate, growth_area, penndot_project, cdbg_investment, flood_zone:** Confirm source data is current, validate proximity/intersection, contextualize significance.

**conservation_easement, ag_security:** Confirm restriction is still active, check proceedings for removal/modification requests.

### Output
- `public.evidence` — one row per validated signal per parcel with: claim, evidence_data (JSONB), source_url, validation_status (confirmed/upgraded/downgraded/stale/irrelevant), adjusted_significance (high/medium/low/none), validation_reasoning, cross_references

### Filtering
If all signals on a parcel are downgraded to low/none, that parcel is skipped by Pass 3. The old scoring system's useful function (ranking what's worth writing about) survives as a filter, not a user-facing number.

## Pass 3: Brief Generation

**Purpose:** Synthesize validated signals into an intelligence brief that a developer can act on.

**Unit:** Per parcel (only parcels with at least one medium or high significance validated signal).

### Harness Structure
The prompt receives:
- Parcel fundamentals
- Entity profile (canonical name, type, portfolio summary)
- All Pass 2 validated signals (sorted by significance, excluding irrelevant)
- Each signal includes: key, validation status, significance, reasoning, key facts, cross-references, internal URL, source URL

### Constraints Enforced by the Harness
1. Every factual claim must reference a specific signal using `[Signal: signal_key]` citation
2. No invented market values, projections, timelines, or comparables
3. No legal or financial advice — observations only
4. Conflicting signals (e.g., development pressure + flood zone) must be addressed, not ignored

### Output
- `public.parcel_briefs` — narrative brief text with citations, qualitative assessment, assessment reasoning, key questions (things the reader should verify), citation array (claim -> signal -> internal URL -> external URL), generation metadata (model used, pass versions, timestamp)

### Assessment Categories
- `strong_opportunity` — multiple confirmed high-significance signals converging, minimal constraints
- `emerging` — 1-2 confirmed signals suggesting early-stage activity, worth monitoring
- `speculative` — signals present but significance uncertain or mixed
- `constrained` — opportunity exists but significant barriers
- `not_actionable` — signals weak, stale, or contradicted by constraints

## Pass 4: County Narratives

**Purpose:** Detect cross-parcel patterns that no single parcel brief reveals.

**Unit:** Per geography or per theme. Runs after all Pass 3 briefs are complete.

### Four Detection Scans

#### Scan A: Corridor Activity
Groups parcels with shared signal types within 500m of each other. Identifies corridor-level development trends. SQL clusters parcels spatially, gathers their briefs and relevant proceedings, LLM synthesizes the corridor story.

Minimum: 3 parcels with shared signals within 500m.

Questions for LLM: Is activity coordinated or independent? Accelerating, steady, or stalling? What's the corridor-level story beyond individual parcels?

#### Scan B: Owner Portfolio
Identifies entities whose portfolio tells a story — concentrated distress, active assembly, cross-municipality positioning.

Triggers: Entity with 3+ briefed parcels AND (2+ distressed parcels OR 2+ recent acquisitions OR holdings across 3+ municipalities).

Questions for LLM: What's the entity's strategy? Timeline of activity? Expanding, holding, or unwinding? Impact on other players in the same areas?

#### Scan C: Municipal Trends
Per-municipality analysis of development posture using ZHB decision patterns, assessment distribution across parcels, signal distribution, and distress summary.

Questions for LLM: Pro-growth, stagnant, or distressed? What do ZHB decisions reveal? Where's the tension? What should someone watching this municipality know?

#### Scan D: Distress Migration
County-wide analysis using SCD Type 2 history to compare current vs 90-day-prior tax distress snapshots by municipality and school district.

Triggers: Municipality with 5+ parcel change or $10K+ owed change in 90 days.

Questions for LLM: Where is distress concentrating vs resolving? Any disproportionate school district impact? Spreading geographically or deepening? Where are forced sales most likely in 6-12 months?

### Output
- `public.county_narratives` — title, body, narrative_type, trajectory, affected_pidns, key_entities, citations, generated_at, expires_at

### Staleness
- Narratives regenerate weekly after full Pass 1-3 pipeline completes
- Skip municipalities with no underlying data changes
- 14-day default expiration, 7-day age label in frontend

## Data Architecture

### New Tables

#### Intelligence Output Tables

**public.evidence**
- `id SERIAL PRIMARY KEY`, `pidn TEXT NOT NULL`, `signal_key TEXT NOT NULL`, `claim TEXT`, `evidence_data JSONB`, `source_url TEXT` (external), `internal_url TEXT`, `validation_status TEXT` (confirmed/upgraded/downgraded/stale/irrelevant), `adjusted_significance TEXT` (high/medium/low/none), `validation_reasoning TEXT`, `cross_references JSONB`, `validated_at TIMESTAMPTZ`
- Unique constraint on `(pidn, signal_key)` — one validated evidence record per signal per parcel

**public.parcel_briefs**
- `pidn TEXT PRIMARY KEY`, `brief_text TEXT`, `assessment TEXT` (strong_opportunity/emerging/speculative/constrained/not_actionable), `assessment_reasoning TEXT`, `key_questions TEXT[]`, `signal_count INT`, `citations JSONB`, `brief_version INT`, `generated_at TIMESTAMPTZ`, `pass_metadata JSONB` (which passes ran, model used)

**public.county_narratives**
- `narrative_id SERIAL PRIMARY KEY`, `title TEXT`, `body TEXT`, `narrative_type TEXT` (corridor/municipality/owner_portfolio/market_segment), `trajectory TEXT`, `affected_pidns TEXT[]`, `key_entities TEXT[]`, `citations JSONB`, `generated_at TIMESTAMPTZ`, `expires_at TIMESTAMPTZ`

**public.entity_graph**
- `entity_id SERIAL PRIMARY KEY`, `canonical_name TEXT`, `entity_type TEXT` (person/business/trust/government), `linked_names TEXT[]`, `linked_sources JSONB`, `relationships JSONB`, `verification_status TEXT`, `verification_reasoning TEXT`, `verified_at TIMESTAMPTZ`

#### Pipeline Tracking

**meta.intelligence_passes**
- `pidn TEXT`, `pass_number INT`, `status TEXT` (pending/running/complete/failed), `last_run_at TIMESTAMPTZ`, `input_hash TEXT`, `error_message TEXT`

#### New Staging Tables

**staging.corporate_entities**
- `entity_name TEXT`, `entity_number TEXT`, `entity_type TEXT`, `status TEXT`, `formation_date DATE`, `registered_agent_name TEXT`, `registered_agent_address TEXT`, `office_address TEXT`, `officers JSONB`, `source_url TEXT`, `valid_from TIMESTAMPTZ DEFAULT NOW()`, `valid_to TIMESTAMPTZ`

**staging.public_proceedings**
- `id SERIAL PRIMARY KEY`, `body_name TEXT`, `meeting_date DATE`, `proceeding_type TEXT`, `raw_text TEXT`, `source_url TEXT`, `document_url TEXT`, `valid_from TIMESTAMPTZ DEFAULT NOW()`, `valid_to TIMESTAMPTZ`

**staging.proceeding_extractions**
- `id SERIAL PRIMARY KEY`, `proceeding_id INT REFERENCES staging.public_proceedings(id)`, `extraction_type TEXT`, `applicant_name TEXT`, `parcel_reference TEXT`, `current_zoning TEXT`, `proposed_zoning TEXT`, `decision TEXT`, `conditions JSONB`, `supporting_text TEXT`, `extraction_confidence FLOAT`, `model_used TEXT`, `page_number INT`

#### Modifications to Existing Tables
- All existing staging tables gain `source_url TEXT` column, backfilled from county_config URLs

### Tables Deprecated
- `public.development_momentum` — replaced by `public.parcel_briefs` + `public.evidence`
- `public.development_signals` — replaced by `public.evidence`

## API Changes

### New Endpoints

**GET /api/briefs/{pidn}**
Returns the parcel intelligence brief, assessment, evidence array with internal + external links, generation metadata.

**GET /api/briefs/feed**
Paginated feed of parcel briefs. Filterable by municipality, assessment type, signal type. Sorted by generation date and signal strength (internal ranking, not exposed).

**GET /api/narratives**
County-level narratives. Filterable by narrative_type (corridor/municipality/owner_portfolio/market_segment). Paginated.

**GET /api/evidence/{pidn}**
All validated evidence records for a parcel, each with claim text, validation status, validation reasoning, and both source links.

### Modified Endpoints

**GET /api/parcels/{pidn}**
Adds `brief` and `evidence` fields to existing response. Structured data stays (assessment, tax records, flood, structures).

**GET /api/stats**
Shifts to reflect intelligence layer: count of active briefs, strong opportunities, new narratives this week, plus existing data source counts.

### Deprecated Endpoints
- `GET /api/scores/distressed` — replaced by briefs feed filtered by signal type
- `GET /api/scores/development` — replaced by briefs feed
- `GET /api/scores/opportunity` — replaced by briefs feed
- `GET /api/scores/assemblage` — assemblage becomes a signal type within evidence
- `GET /api/scores/municipalities` — replaced by narratives filtered by municipality type

## Migration Path

### Phase 1: Data Foundation
1. Build PA DOS corporate entity scraper + staging table
2. Build public proceedings scraper (all 72 municipalities) + staging table
3. Build multimodal extraction pipeline (Gemma 4, proceeding_extractions)
4. Add `source_url` column to all existing staging tables, backfill
5. Alembic migration for all new tables

Existing product runs unchanged during this phase.

### Phase 2: LLM Infrastructure
1. Set up self-hosted model on 4090 for development
2. Build harness framework (prompt templates, structured output parsing, retry/failure handling, Dagster asset wrappers)
3. Build Pass 0 (document extraction)
4. Build Pass 1 (entity verification) — run against current data, validate quality
5. Build Pass 2 (signal validation) — compare LLM judgments against current weighted scores
6. Build Pass 3 (brief generation) — iterate on quality with ~100 parcel test set
7. Build Pass 4 (county narratives) — generate from test set
8. Set up Hetzner VPS with quantized model for production, wire into Dagster schedule

### Phase 3: API Transition
1. Add new endpoints (briefs, narratives, evidence) alongside existing
2. Add brief/evidence fields to existing parcels endpoint
3. Old score endpoints stay live but unlinked from frontend

### Phase 4: Frontend Transformation
1. Property detail: replace momentum widget with brief section
2. Homepage: replace stat cards with county briefing
3. New `/intelligence` page replaces Radar, Distressed, Assemblage
4. Map popups: brief headline + assessment
5. Owner profile: entity verification results
6. Remove score-based pages from navigation

### Phase 5: Cleanup
1. Deprecate and remove old score endpoints
2. Drop `public.development_momentum` and `public.development_signals`
3. Remove signal weight constants from codebase
4. Update ops health to monitor LLM pipeline passes

## Failure Handling

- If a pass fails for a parcel, retry once with same input. If fails again, flag in `meta.intelligence_passes` and keep previous brief (stale but present).
- If LLM produces invalid JSON/structure, log as harness failure, don't surface to users.
- Brief staleness: briefs older than 2 weeks without data change get "Last verified: [date]" label. Briefs older than 4 weeks get flagged for re-generation regardless of input hash.

## Cost Considerations

- Self-hosted LLM: 8GB Hetzner VPS (~$8-12/mo) for production inference
- No per-token API costs for brief generation (self-hosted)
- OpenRouter costs for search remain (separate concern)
- Primary compute cost: electricity for 4090 during development/iteration
- Scale: ~176K parcels but only parcels with medium+ signals get briefs (estimated 10-30K)
- County narratives: ~72 municipalities + portfolio scans + distress scan = small batch weekly
